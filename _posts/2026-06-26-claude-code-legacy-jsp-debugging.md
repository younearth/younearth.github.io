WSL2 + Claude Code 환경에서 JSP 기반의 레거시 웹 시스템을 유지보수하면서, 단순한 "AI한테 코드 짜달라고 하기"를 넘어서는 여러 일들을 겪었다. Bash 명령어 승인 프롬프트가 왜 뜨는지, headless 브라우저로 실제 화면을 검증하는 게 왜 이렇게 험난했는지, 그리고 수십 개 JSP 파일에 일괄적으로 문서화 작업을 시키면서 마주친 함정들을 정리해본다.

## 1. Claude Code의 승인 프롬프트, 그냥 넘기지 말고 읽어보자

Claude Code는 터미널 명령을 실행하기 전에 항상 이런 화면을 띄운다.

```
Bash command
  <실행할 명령어>
  <한 줄 요약>

Do you want to proceed?
> 1. Yes
  2. Yes, and don't ask again for: ...
  3. No
```

처음엔 그냥 "Yes"만 누르고 넘어갔는데, 가만 보니 경고 문구의 종류가 꽤 다양하다는 걸 알게 됐다.

- `This command changes directory before running git, which can execute untrusted hooks...` → `cd && git ...` 패턴에 대해 항상 뜨는 표준 경고. git이 저장소의 `.git/hooks/`에 등록된 스크립트를 자동 실행할 수 있다는 일반적 보안 안내일 뿐, 매번 실제로 위험한 건 아니다.
- `Contains shell syntax (file_redirect) that cannot be statically analyzed` → heredoc(`cat <<'EOF' > file`)처럼 셸 리다이렉트가 섞인 명령에 대해 정적 분석기가 100% 검증하지 못한다는 주의 문구.
- `Contains brace with quote character (expansion obfuscation)` → JS 코드 안의 `{ chromium }` 같은 객체 구조분해 문법을, 탐지기가 셸 차원의 중괄호 난독화 패턴으로 오인해서 뜨는 경고. heredoc 구분자를 `'EOF'`처럼 따옴표로 감싸면, 안의 내용은 셸이 전혀 해석하지 않고 순수 텍스트로만 취급된다는 걸 알면 안심할 수 있다.

결론: 경고 문구는 "위험하다"는 확정 판단이 아니라 "자동 분석기가 끝까지 보장 못 하니 사람이 한 번 보라"는 신호다. 명령어 내용을 직접 읽고, 격리된 임시 폴더(`/tmp/.../scratchpad`)에서 일어나는 읽기 전용 작업인지 확인하는 습관이 중요하다.

## 2. 실전 디버깅: 합계 행이 깨지는 이유는 `<colgroup>`이었다

화면의 한 테이블에서, 다른 테이블은 정상인데 특정 테이블의 합계(총계) 행만 셀이 쌓여 보이는 버그가 있었다. Claude Code가 JSP, JS, SQL 매퍼를 모두 훑어본 결론은 의외로 단순했다.

- 정상 테이블: `<colgroup>`의 모든 열에 **명시적 너비(예: `20%`)**가 지정되어 있음
- 깨지는 테이블: 일부 열들에 너비 지정이 없음

`table-layout: auto`이고 너비 힌트가 없으면, 브라우저는 페이지가 처음 그려지는 시점에 보이는 내용만으로 열 너비를 확정한다. 그런데 문제의 열은 AJAX 응답이 오기 전까지 비어 있는 상태라, 브라우저가 빈 칸 기준으로 좁게 너비를 잡아버린다. 이후 늦게 도착한 긴 값이 이미 고정된 좁은 너비와 충돌하면서 셀이 깨져 보이는 것이었다.

교훈: 비동기로 채워지는 데이터 열에는 항상 `<colgroup>`에 명시적 너비를 지정해야 한다. 안 그러면 "타이밍에 따라 가끔 깨지는" 가장 재현하기 어려운 종류의 버그가 된다.

## 3. Headless 브라우저로 직접 검증하기 — 그리고 그 과정의 함정들

코드만 보고 "이렇게 고치면 될 것 같다"가 아니라, 실제로 렌더링된 화면을 캡처해서 확인하고 싶었다. Playwright + Chromium으로 이 작업을 했는데, 생각보다 많은 환경 문제를 만났다.

### 3-1. WSL2에서 `sudo`가 비대화형 셸이라 실패한다

Claude Code의 Bash 도구는 비대화형(non-interactive) 셸에서 동작한다. 그래서 `sudo apt-get install ...`을 실행하면 비밀번호를 입력받을 TTY를 못 찾고 그냥 실패한다.

```
sudo: a password is required
```

해결책은 단순했다 — 별도의 WSL 터미널 창을 직접 열어서, 거기서 sudo 명령을 입력하는 것. Claude Code가 대신 비밀번호를 입력해줄 수는 없다.

### 3-2. 패키지명이 Ubuntu 버전마다 다르다

```
E: Unable to locate package libasound2t64
```

`libasound2t64`는 Ubuntu 24.04(noble) 이후에 생긴 패키지명이고, 우리 환경은 22.04(jammy)였다. 예전 이름인 `libasound2`로 바꾸니 해결됐다. `apt-get install pkg1 pkg2 pkg3 ...`처럼 여러 패키지를 한 줄에 나열하면, 그중 하나라도 못 찾으면 전체가 실패한다는 점도 기억해둘 만하다.

### 3-3. Claude Code의 Bash 세션과 내가 연 터미널이 "다른 환경"일 수 있다

설치를 끝냈다고 알렸는데도 Claude Code가 라이브러리 설치 확인 결과가 없다고 보고하는 일이 있었다. 알고 보니 Claude Code의 Bash 도구가 보는 셸 환경과, 사용자가 직접 연 터미널이 서로 다른 네임스페이스/세션이었던 것. 같은 머신이라도 두 프로세스가 완전히 같은 환경을 공유하지 않을 수 있다는 걸 처음 알았다.

## 4. 이분 탐색(bisection)으로 CSS 버그 원인 좁히기

공통 CSS 파일이 혹시 추가로 영향을 주는지 확인할 때 쓴 방법이 인상적이었다.

```bash
head -n 2000 common.css > common_half1.css
tail -n +2001 common.css > common_half2.css
```

CSS를 앞/뒤 절반으로 쪼개서, 각각 적용한 두 개의 테스트 HTML을 만들고 따로 스크린샷을 떠서 비교했다. 어느 절반에서 문제가 재현되는지 확인한 다음, 그 절반을 또 절반으로 쪼개가는 식으로 — 이진 탐색으로 원인이 되는 CSS 규칙을 좁혀가는 디버깅 기법이다. 코드 리뷰만으로 찾기 어려운 전역 스타일 충돌을 잡을 때 효과적이었다.

## 5. 수십 개 JSP 파일에 문서화 헤더 일괄 적용하기

비슷한 패턴의 JSP 파일이 40개 넘게 있어서, Claude Code에게 한 번에 헤더 주석 가이드를 적용하는 작업을 맡겼다. 파일마다 검증 단계를 두는 게 핵심이었는데, 의외로 함정이 많았다.

### 5-1. JSP의 EL 표현식이 JS 문법 검사를 방해한다

`<script>` 안의 JS 코드를 Node.js로 문법 검사하려 했더니, JSP의 EL(Expression Language) 문법인 `${...}`를 JS의 템플릿 리터럴로 오해해서 검사기가 잘못된 오류를 냈다. `${` → `$_{`로 임시 치환해서 "무력화"한 다음 검사하는 우회법을 썼다.

### 5-2. 줄바꿈 문자(CRLF) 때문에 정규식이 오탐을 낸다

```bash
# 수정 전 — 정상적인 박스 주석도 "없음"으로 오판
awk '... if (prev !~ /\*\/$/) ...'

# 수정 후 — CRLF의 \r까지 고려
awk '... if (prev !~ /\*\/\r?$/) ...'
```

Windows 환경에서 작업된 파일이라 줄 끝에 보이지 않는 `\r`(캐리지 리턴)이 있었다. 정규식이 "줄 끝(`$`)"을 인식하는 데 이 문자가 끼어들어서, 실제로는 정상인 주석을 "누락됨"으로 잘못 판단했던 것. Windows에서 작성된 텍스트 파일을 Linux 도구로 정규식 처리할 때는 CRLF를 항상 의심해야 한다는 교훈을 얻었다.

### 5-3. JSP 전용 태그도 JS 문법 검사 전에 걸러내야 한다

`<%-- JSP 주석 --%>`, `<jsp:include .../>` 같은 JSP 전용 문법이 `<script>` 블록 안에 섞여 있으면 순수 JS 파서가 당연히 이해하지 못한다. 검사 전에 정규식으로 미리 제거하는 전처리 단계를 추가해야 했다.

```python
js = re.sub(r'<%--.*?--%>', '', js, flags=re.S)
js = re.sub(r'<jsp:include[^>]*>', '', js)
```

### 5-4. 함수 네이밍 규칙이 파일마다 다르다

함수 접두사 규칙(예: `fn_`, `_fnc_` 등)이 파일마다 달라서, 검증용 정규식도 매번 파일에 맞게 조정해야 했다. 일괄 작업이라고 해서 패턴이 100% 동일하지는 않다는 걸 새삼 느꼈다.

## 6. 알아두면 유용한 Claude Code 조작법

작업 도중 실수로 막혔던 부분들도 정리해둔다.

- **Shift+Tab**: "Yes/No" 메뉴와 별개로, 세션 전체의 동작 모드(기본 ↔ 자동 승인 ↔ Plan)를 순환시키는 단축키. 잘못 눌러서 화면 하단에 `accept edits on`이 뜨면, Shift+Tab을 다시 눌러서 기본 모드로 돌아오면 된다.
- **`/permissions`**: "Yes, and don't ask again for..."를 잘못 눌렀을 때, 저장된 자동 승인 규칙 목록을 확인하고 지울 수 있는 슬래시 명령. 세션이 끝나도 `.claude/settings.local.json`에 영구 저장되므로, 가끔 점검해주는 습관이 필요하다.

## 마무리

이번 작업을 통해 느낀 건, Claude Code의 승인 프롬프트가 단순한 "허락 받기" 절차가 아니라 명령어가 실제로 무엇을 하는지 한 번 더 들여다보게 하는 안전장치라는 점이다. 특히 WSL2 + Windows 마운트 경로 조합에서는 패키지명 차이, 셸 네임스페이스 분리, CRLF 같은 환경 특성 문제가 코드 자체의 버그보다 더 자주 발목을 잡았다. AI에게 작업을 맡기더라도, 그 결과를 검증하는 방법(헤드리스 브라우저 스크린샷, 이분 탐색, 정규식 교차 검증)을 같이 갖춰두는 게 결국 신뢰할 수 있는 결과로 이어진다는 걸 다시 확인한 한 주였다.
