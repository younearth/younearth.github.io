## 들어가며

"AI에게 무엇을 시킬지 고민하는 것"에서 "AI를 지시하는 시스템 자체를 설계하는 것"으로 관점이 바뀌면 어떨까?

오늘은 **Loop Engineering** 개념을 실제로 적용해서, 특정 도메인의 콘텐츠를 자동으로 생성하는 파이프라인을 Claude Code로 구축한 과정과 배운 점을 공유한다.

---

## Loop Engineering이란?

핵심 개념은 단순하다. *"내 역할은 루프를 짜는 것이다."*

기존 프롬프트 엔지니어링이 "AI에게 어떻게 물어볼까"에 집중했다면, Loop Engineering은 **AI가 반복적으로 잘 작동하도록 시스템 자체를 설계**하는 것이다.

루프를 구성하는 요소는 크게 여섯 가지다.

| 요소 | 역할 |
|------|------|
| **스킬(Skill)** | 재사용 가능한 프로젝트 지식과 작업 규칙 |
| **오토메이션** | 반복 작업의 트리거 |
| **워크트리** | 작업별 독립 환경 |
| **서브에이전트** | 역할 분리된 별도 AI |
| **플러그인/커넥터** | 외부 도구 연결 |
| **상태 파일** | 세션 간 연속성 확보 |

이 여섯 가지 중 오늘 파이프라인에 직접 적용한 건 **스킬, 서브에이전트, 상태 파일** 세 가지다.

---

## 파이프라인 설계

### 목표

특정 도메인에 맞는 콘텐츠(블로그 포스트, SNS 캡션)를 주제 입력만으로 자동 생성하는 워크플로우 구축.

### 전체 흐름

```
주제 + 플랫폼 입력
    ↓
유형 자동 감지 → 템플릿 로드
    ↓
[에이전트 1] 초안 생성 + 검색 보충
    ↓
[에이전트 2] 품질 검토 + 글자 수 조정
    ↓
사용자 검토 → 발행
    ↓
상태 파일 이동 (drafts → published)
```

### 디렉토리 구조

```
content-pipeline/
├── SKILL.md               # 파이프라인 규칙 및 유형 감지 기준
├── templates/
│   ├── platform-a/        # 플랫폼별 포맷 템플릿
│   │   ├── type-1.md
│   │   ├── type-2.md
│   │   └── type-3.md
│   └── platform-b/
│       ├── type-1.md
│       ├── type-2.md
│       └── type-3.md
├── drafts/                # 검토 대기 초안
└── published/             # 발행 완료 기록
```

### Claude Code 스킬 커맨드

`~/.claude/commands/content-pipeline.md`에 작업 흐름을 정의하면 `/content-pipeline`으로 호출 가능해진다.

```markdown
# /content-pipeline

## STEP 1 — 입력 수집
## STEP 2 — 유형 감지
## STEP 3 — 템플릿 로드
## STEP 4 — [에이전트 1] 초안 생성
## STEP 4-S — 정보 부족 시 검색 보충
## STEP 5 — [에이전트 2] 검토 + 글자 수 조정
## STEP 6 — 파일 저장 (.txt / .json)
## STEP 7 — 출력
```

## 핵심 구현 포인트

### 1. 실제 데이터로 템플릿 학습

처음에는 일반적인 포맷으로 템플릿을 만들었다. 그런데 실제로 쓸 사람의 기존 콘텐츠를 분석하고 나서 템플릿을 완전히 다시 써야 했다.

**교훈:** 템플릿은 "일반적으로 좋은 포맷"이 아니라, **실제 작성자의 스타일을 그대로 반영**해야 한다. AI가 스타일을 흉내 내려면 충분한 예시 데이터가 필요하다.

### 2. 멀티에이전트 역할 분리

하나의 에이전트가 초안 작성과 검토를 동시에 하면 자기 편향이 생긴다. 역할을 분리했다.

- **에이전트 1 (작성자)**: 템플릿 기반 초안 생성에만 집중
- **에이전트 2 (검토자)**: 톤, 포맷, 품질, 글자 수 검토

별도 프로세스를 띄운 게 아니라 같은 컨텍스트 내에서 역할을 명시적으로 전환하는 방식이다. 그래도 "검토자 모드"로 전환하는 것만으로 초안의 문제점을 더 잘 잡아냈다.

### 3. 검색 보충 + 사실/의견 분리

사용자가 입력한 정보가 부족할 때 WebSearch로 보충하되, 규칙을 엄격히 정했다.

```
검색으로 가져올 수 있는 것: 영업시간, 주소, 메뉴, 가격 등 사실 정보
검색으로 가져오면 안 되는 것: 다른 글의 표현, 감상, 평가
```

보충된 항목은 `[검색 보충]`으로 표시해서 사용자가 확인 후 발행하도록 했다.

### 4. 상태 파일로 세션 간 연속성 확보

AI 에이전트는 세션이 끊기면 컨텍스트를 잃는다. *"에이전트는 잊지만 저장소는 기억한다."*

초안은 항상 `drafts/`에 저장하고, 발행 완료 시 `published/`로 이동한다. 덕분에 어떤 글이 작성 중인지, 어떤 글이 발행됐는지 세션과 무관하게 추적 가능하다.

파일 포맷도 목적에 따라 분리했다.
- **`.txt`**: 복붙해서 바로 쓸 수 있는 본문
- **`.json`**: 메타데이터 및 검색 보충 항목 기록

### 5. 품질 제약 조건

글자 수 범위(예: 1000~1500자)를 에이전트 검토 단계에서 강제했다. 이렇게 하면 에이전트가 알아서 너무 짧으면 보강하고, 너무 길면 압축한다. 품질 기준을 사람이 매번 판단하지 않아도 된다.

## 배운 점

**1. 루프를 먼저 설계하고, 콘텐츠는 나중에 채워라**

파이프라인 구조(스킬, 템플릿, 상태 파일)를 먼저 만들고 나면, 실제 콘텐츠 생성은 훨씬 빠르고 일관성 있게 된다.

처음부터 "좋은 글"을 만들려고 하면 매번 처음부터 시작하는 셈이다. 반면 루프가 있으면 입력만 바꿔도 일정한 품질이 나온다.

---

**2. 템플릿은 "좋은 예시"가 아니라 "내 스타일"로**

일반적인 베스트 프랙티스보다 실제 작성자의 기존 글에서 패턴을 추출해서 만든 템플릿이 훨씬 자연스러운 결과물을 낸다.

이번에 처음 만든 템플릿과 기존 글을 분석한 후 다시 만든 템플릿의 결과물은 완전히 달랐다. AI가 스타일을 흉내 내려면 충분한 예시 데이터가 필수다.

---

**3. 검색 보충은 사실 정보에만, 판단은 사람이**

AI가 다른 사람의 후기나 표현을 가져오면 저작권 문제와 부정확성이 생긴다.

검색 활용 범위를 명확히 제한하고(사실 정보만), 보충된 항목을 사용자가 확인하는 단계를 두는 것이 중요하다. 자동화와 신뢰성은 트레이드오프가 있다.

---

**4. 검증 책임은 여전히 사람에게**

루프가 아무리 잘 설계되어 있어도, 발행 전 사람이 최종 확인하는 단계는 생략하면 안 된다.

자동화는 속도와 일관성을 높이는 것이지, 판단을 대체하는 게 아니다. "인지적 항복"—생각을 기계에 전적으로 넘기는 것—이 가장 큰 위험이다.

## 마치며

처음엔 "AI한테 글 써달라고 하면 되는 거 아닌가?"라고 생각했다. 그런데 막상 파이프라인을 만들고 나니, 잘 설계된 루프가 단순한 프롬프트와 얼마나 다른 결과를 만드는지 체감할 수 있었다.

다음 단계로는 오토메이션(스케줄 트리거)과 플러그인 연결을 추가해볼 생각이다. 루프는 계속 발전한다.
